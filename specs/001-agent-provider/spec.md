# Feature Specification: Agent Provider(大模型统一接入层)与 Profile 加载

**Feature Branch**: `001-lesson16-agent-provider`

**Created**: 2026-10-03

**Status**: Draft

**Input**: 第16节需求:Agent 与大模型之间的统一接入层,同时交付 Profile(Agent 配置)的解析加载,并为每次模型调用留下审计记录。

## Clarifications

### Session 2026-10-03

- Q: 全局层声明的某家提供方,其凭证环境变量未设置时启动如何处理? → A: 跳过该提供方并记错误日志,启动不阻断;该提供方不进名称到模型的映射表,引用它的 Profile 按"提供方在全局层找不到"处理。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 按 Agent 配置路由到指定的大模型(Priority: P1)

运维在同一实例上同时接入了两家大模型(如 deepseek 与 kimi)。不同 Agent 的配置各自指定使用其中一家。上层只需"传入会话、Agent 配置、提示内容",就能拿到模型响应,无需关心具体是哪家、接口格式有何差异。

**Why this priority**: 这是整个 Provider 存在的理由,也是 ReAct 循环每一轮的依赖;没有它,Agent 无法思考。

**Independent Test**: 配置两家模型(测试中用替身),分别用指定不同提供方的 Agent 配置发起调用,验证被指定的一家被调用 1 次、另一家 0 次;使用未接入的提供方名称时得到明确异常。

**Acceptance Scenarios**:

1. **Given** 实例接入了 deepseek 与 kimi,**When** 以指定 kimi 的 Agent 配置发起一次调用,**Then** 只有 kimi 被调用一次,deepseek 一次都不被触碰,响应原样返回给调用方。
2. **Given** Agent 配置引用了一个未接入的提供方名称,**When** 发起调用,**Then** 立即得到指明该名称的明确异常,不会静默改用其他模型。
3. **Given** 提示内容中携带了可用工具的说明,**When** 发起调用,**Then** 工具说明被翻译为模型可理解的格式随请求发出,且底层框架的"自动执行工具"被关闭;模型若回复"想调用某工具",该请求原样交回上层,Provider 自己不执行任何工具。

---

### User Story 2 - 每次模型调用留下审计记录,失败同样留痕(Priority: P1)

安全与合规人员需要事后追查任意一次模型调用:用了哪家、哪个模型、消耗多少 token、耗时多久、是否成功。某次调用因超时或限流失败时,审计里必须能查到这次失败及原因,同时失败仍如实上报给上层。

**Why this priority**: "可审计"是系统的核心差异化能力,要求从第一天就落库;只记成功不记失败会让真实事故毫无痕迹。

**Independent Test**: 分别模拟一次成功调用与一次失败调用,检查审计记录:成功条为 success=true 并含提供方/模型/token/耗时;失败条为 success=false 并含错误原因,且调用方同时收到异常。

**Acceptance Scenarios**:

1. **Given** 一次调用成功,**When** 调用结束,**Then** 审计表新增一条关联该会话的记录,含提供方、模型、token 用量、耗时,success=true。
2. **Given** 一次调用因超时失败,**When** 异常发生,**Then** 审计表先落一条 success=false 且含失败原因的记录,随后同一异常继续抛给上层。
3. **Given** 审计表通过手工维护的建表脚本创建,**When** 读写一条记录,**Then** 能正常存取,且 success 与 error_message 两列真实存在。

---

### User Story 3 - 启动时加载 Agent 配置,坏配置不拖垮整体(Priority: P2)

管理员在配置目录里放了若干 Agent 配置文件。启动时系统逐个解析校验,合法的进入内存索引、可按名称查找;写错了提供方名称的那个得到清晰的错误日志,但不阻断启动,也不影响其他合法配置。

**Why this priority**: Provider 是第一个消费 Agent 配置的模块,需要先有加载能力才能被端到端使用;但相比调用与审计,它不改变核心调用行为,故次之。

**Independent Test**: 在临时目录放置一份全字段合法配置、一份引用不存在提供方的配置、一份格式损坏的文件,执行加载,验证合法配置全字段解析且可按名查到,另两份产生明确错误日志且不影响前者。

**Acceptance Scenarios**:

1. **Given** 目录中有一份含全部字段的合法配置,**When** 启动加载,**Then** 全部字段被正确解析,并可按名称从内存索引查到。
2. **Given** 某配置引用的提供方名称在全局层不存在,**When** 启动加载,**Then** 记录指明配置文件与提供方名称的错误日志,该配置不入索引,启动不被阻断。
3. **Given** 目录中同时有损坏文件与合法文件,**When** 启动加载,**Then** 损坏文件被记录错误并跳过,其余合法配置照常加载。
4. **Given** 配置值中含 `${ENV}` 形式的占位,**When** 解析,**Then** 占位从环境变量取值;代码与配置文件中不出现明文密钥。

---

### Edge Cases

- 全局层同一提供方名称重复声明时,必须明确报错,保证"名称到模型"一一对应。
- 全局层引用的凭证环境变量未设置时,该提供方被跳过并记指明提供方名称与缺失变量名的错误日志,不以空值悄悄运行;启动不阻断,其他提供方不受影响;引用该提供方的 Profile 按"提供方找不到"报错、不入索引,直接调用该名称时抛明确的提供方不存在异常。
- 配置目录不存在或为空时,启动不失败,索引为空。
- 两个配置文件声明了相同的 name 时,后者不得静默覆盖前者,需记录错误日志。
- 模型调用失败但审计写入本身也失败时,不得吞掉原始调用异常。
- 响应不含 token 用量信息时,审计记录用量为空而非报错。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Agent 配置(Profile)MUST 承载全部字段:name、description、identity、provider(name/model/temperature)、tools、skills、mcp_servers、channels、notify_channels、schedules、bootstrap、settings;本节建全类型,后续各节按需取用。
- **FR-002**: 系统 MUST 在启动时扫描 Agent 配置目录下所有 YAML 并解析为 Profile;逐个校验,本节只校验"所引用的提供方名称能在全局配置层找到";不合法的记错误日志、不阻断启动,其余照常加载。
- **FR-003**: 解析成功的 Profile MUST 进入内存索引并可按 name 查找;本节只有启动扫描这一条注册路径。
- **FR-004**: 配置 MUST 分两层:全局层声明实例接入了哪些提供方及凭证来源(环境变量占位);Profile 层声明该 Agent 用哪个提供方/模型/温度。Profile 引用的提供方名称在全局层找不到 MUST 明确报错。`${ENV}` 占位 MUST 能从环境变量解析,代码与配置文件中 MUST NOT 出现明文密钥。
- **FR-005**: 系统 MUST 对外只提供一个调用入口:传入会话标识、Profile、提示内容,返回模型响应;按 Profile 中的提供方名称显式选择对应模型,名称找不到时直接抛出明确异常。
- **FR-006**: 提供方名称到模型的对应关系 MUST 在启动时显式建表、一一对应,不依赖按类型自动扫描。
- **FR-007**: 系统 MUST 只把可用工具翻译成模型可理解的格式并带上请求,MUST NOT 执行工具;MUST 关闭底层框架的自动工具执行,工具调度权完全留给上层循环。模型返回的"想调用某工具"请求 MUST 原样交回上层。
- **FR-008**: 系统 MUST 提供工具格式适配器:把系统内部工具的参数说明翻译成底层框架的工具描述,字段一一对齐,产物不含任何执行逻辑。
- **FR-009**: 每次模型调用 MUST 落审计记录:成功记提供方、模型、token 用量、耗时、success=true;失败同样记录,success=false 并保存错误信息,随后把原异常继续抛给上层。审计记录按会话关联,含 success 与 error_message 字段。
- **FR-010**: 审计表 MUST 由手工维护的建表脚本创建,MUST NOT 依赖框架自动建表或自动迁移。

**明确不做(边界)**:

- fallback(一家挂了换另一家)、hedge racing(同时发多家抢最快)、熔断,均放扩展阶段;故障直接把错误抛给上层。
- 成本看板放后续阶段,眼下只落审计表。
- Profile 的运行时 register() 方法(第 29 节补)。
- Profile 除提供方引用之外的字段校验规则(各节自补)。
- 工具的真正执行(属后续节的工具执行器)。

### Key Entities

- **Profile(Agent 配置)**: 一个 Agent 的完整声明,以 name 为唯一标识;含身份、所用提供方(名称/模型/温度)、工具、技能、外部工具服务、接入渠道、通知渠道、定时计划、引导文件、运行设置等。
- **全局提供方声明**: 实例级配置,每项含唯一的提供方名称与凭证来源(环境变量占位);Profile 通过名称引用。
- **Profile 索引**: 启动后驻留内存的 Profile 集合,按 name 查找。
- **模型调用审计记录**: 一次模型调用的事实记录,关联会话,含提供方、模型、token 用量、耗时、是否成功、失败原因。
- **提示内容与模型响应**: 上层传入的待发送内容(含可用工具说明)与模型返回的结果(可能含"想调用某工具"的请求与 token 用量)。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在同时接入两家模型的场景下,100% 的调用落到 Profile 指定的那一家,未指定一家的调用次数为 0。
- **SC-002**: 对未接入的提供方名称,100% 在调用前即得到指明该名称的明确异常,不出现静默回退。
- **SC-003**: 每一次模型调用(成功或失败)恰好对应一条审计记录;失败调用 100% 带有非空失败原因,且调用方同时收到异常。
- **SC-004**: 在任何带工具说明的调用中,自动工具执行均为关闭,模型要求的工具调用 0 次由 Provider 层执行(不会出现工具被执行两次)。
- **SC-005**: 配置目录中混有合法、引用错误、损坏三类文件时,100% 的合法配置被加载,每个坏文件均产生一条指明文件与原因的错误日志,启动成功。
- **SC-006**: 代码与配置文件中搜索不到任何明文密钥;凭证仅来自环境变量。
- **SC-007**: 自动化测试套件(不依赖真实网络)全部通过,且覆盖上述 SC-001~SC-005;真实模型的冒烟测试单独标记,日常与持续集成中跳过。

## Assumptions

- 第 16 节无前序节依赖;系统内部"工具"的抽象(含参数说明)在本节仅作为适配器的输入形态被消费,其正式交付归后续节,本节只使用其参数说明这一最小契约(此点在 plan 阶段需与代码库核对)。
- 底层依赖 Spring AI Alibaba,项目已锁定其版本集;所接入的具体提供方对应的依赖是否存在于锁定版本集中,须在动手前用依赖树验证,不照教程示例名称假设可用。
- 教程中的 deepseek/kimi/qwen 仅为提供方名称示意,以依赖验证后实际可接入的为准。
- 凭证一律通过环境变量提供;未设置时对应提供方被跳过并记错误日志,不阻断启动(已澄清)。
- 同步阻塞调用模型,一次调用只发起一次请求,不做重试。
- 审计只落库,本节不提供查询接口与报表。
- 持久化使用项目既定的 SQLite;建表脚本随代码维护。
