# Feature Specification: ReAct 循环(第17节)

**Feature Branch**: `002-lesson17-react-loop`

**Created**: 2026-10-04

**Status**: Draft

**Input**: 第17节需求:ReAct 循环——让 Agent 在“想一步、做一步、看结果”的循环里完成多步任务,并保证每一步可审计。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多步任务:先取数据再给建议 (Priority: P1)

用户问“看看今天天气,帮我决定穿什么”。Agent 先判断需要天气数据,调用 HTTP 工具取回数据,看到结果后再给出穿搭建议。模型不需要任何工具即可回答时,一轮就给出最终答复。

**Why this priority**: 这是 Agent 区别于单次问答 chatbot 的核心价值,也是 Demo 一的主链路。

**Independent Test**: 用模拟的模型与工具:第一轮模型要求调工具、第二轮给出文本;确认工具被执行、结果回填进下一轮、最终返回文本;另测无工具调用时一轮收尾。

**Acceptance Scenarios**:

1. **Given** 模型第一轮要求调用某工具、第二轮不再调用, **When** 用户发送消息, **Then** 工具恰好执行一次,其结果出现在第二轮提示中,返回第二轮文本。
2. **Given** 模型首轮即无工具调用, **When** 用户发送消息, **Then** 只调用模型一次并返回其文本。
3. **Given** 一次响应含多个工具调用, **When** 处理该响应, **Then** 按顺序逐个执行(不并行)。

---

### User Story 2 - 边界兜底:死循环、上下文、失败 (Priority: P1)

模型反复要求调工具停不下来时,到最大轮数强制收尾并给出提示;会话历史过长时只保留最近若干轮;某个工具执行失败时,失败原因被记录并作为结果回传给模型,循环不崩溃。

**Why this priority**: 无兜底的循环会死循环、撑爆上下文或因单个工具失败整体崩溃,是生产可用的前提。

**Independent Test**: 模型永远返回工具调用,最大轮数设为 10,断言恰好调用模型 10 次且返回含“达到最大轮数”的提示;构造超过 N 轮的历史,断言提示中只含最近 N 轮。

**Acceptance Scenarios**:

1. **Given** 模型每轮都要求调工具, **When** 处理消息, **Then** 恰好调用模型“最大轮数”次后停止,返回含“达到最大轮数”的文本。
2. **Given** Profile 未指定轮数, **Then** 默认 10;**Given** Profile 指定轮数, **Then** 以 Profile 为准。
3. **Given** 会话历史超过 N 轮(默认 20), **When** 组装提示, **Then** 仅保留最近 N 轮。
4. **Given** 工具执行失败, **When** 循环继续, **Then** 失败原因作为工具结果回填、循环不抛出。

---

### User Story 3 - 全程可审计 (Priority: P1)

每一轮的模型响应、每个工具结果都累积进会话;每次工具调用不论成败都写入审计记录,并带会话标识,可与模型调用审计关联。

**Why this priority**: 可审计是平台的差异化卖点,审计地基必须从第一天立起来。

**Independent Test**: 工具成功与失败各一次,断言各写入一条审计,成功标识与失败原因正确;失败时异常不被吞。

**Acceptance Scenarios**:

1. **Given** 工具执行成功, **Then** 写入一条“成功”审计。
2. **Given** 工具执行失败, **Then** 写入一条“失败”审计并带错误原因,调用方能获得失败信息。
3. **Given** 一次多轮处理完成, **Then** 会话中依序包含用户消息、每轮模型响应与每个工具结果。

---

### User Story 4 - 统一入口与 Agent 身份传递 (Priority: P2)

CLI、Web、定时三种触发源都通过同一个处理入口进入。处理期间工具能得知“当前是哪个 Agent”;处理结束(包括异常结束)必须清除该身份,避免复用同一线程的下一个请求拿到别人的配置;处理完成后会话被持久化。

**Why this priority**: 身份泄漏是只在并发复用时出现的隐蔽缺陷,必须在验收中钉死。

**Independent Test**: 处理期间读取当前 Agent 配置可得;让内部抛异常,断言异常上抛且当前 Agent 身份已清除;正常结束断言会话已保存。

**Acceptance Scenarios**:

1. **Given** 处理进行中, **Then** 工具侧可取到当前 Profile。
2. **Given** 处理中抛出异常, **Then** 异常上抛且当前 Profile 已被清除。
3. **Given** 处理正常结束, **Then** 会话被持久化且当前 Profile 已清除。

---

### User Story 5 - 上下文加载:改完立即生效 (Priority: P2)

提示的第一部分由 Agent 的启动文件(角色/人设等)和技能文件拼成。用户修改这些文件后,下一次对话立即读到新内容;被 Profile 显式引用的技能文件缺失要报错,启动文件缺失至少给出告警,不得静默跳过。

**Why this priority**: 静默丢失人格是最难排查的软故障。

**Independent Test**: 构建一次提示后改写文件,再构建一次,断言读到新内容;引用不存在的技能文件断言报错;缺失启动文件断言有 WARN 日志。

**Acceptance Scenarios**:

1. **Given** 已构建过提示, **When** 修改文件后再次构建, **Then** 读到新内容。
2. **Given** Profile 引用的技能文件不存在, **Then** 报错。
3. **Given** 启动文件缺失, **Then** 记录 WARN 且不静默。

---

### Edge Cases

- 模型响应既无文本又无工具调用:视为无工具调用,返回其(可能为空的)文本,不进入下一轮。
- 模型要调用的工具不存在或不在当前 Profile 可用范围:作为失败结果回填并写失败审计,循环继续。
- 未启用长期记忆:提示组装时跳过该部分,不报错。
- 工具入参非法或工具抛出异常:按失败处理,原因入审计与回填。
- 提示末尾需带当前日期时间,模型自己不知道今天几号。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 接收用户消息并追加到会话,然后循环:组装提示→调用模型→累积响应;模型没有工具调用时返回最终文本。
- **FR-002**: 系统 MUST 设置最大轮数兜底,默认 10,可由 Profile 覆盖;转满后强制停止,返回含“达到最大轮数”的提示,且调用模型的次数恰好等于最大轮数。
- **FR-003**: 系统 MUST 把每轮模型响应与每个工具结果追加进会话,保证可审计且下一轮可衔接。
- **FR-004**: 系统 MUST 按固定顺序组装提示四部分:(1) 系统提示(角色设定+启动信息+技能,末尾附当前日期时间);(2) 长期记忆(未启用则跳过);(3) 会话历史(仅最近 N 轮,默认 20);(4) 当前 Profile 可用工具列表。长期记忆与会话历史 MUST 明确区分。
- **FR-005**: 工具执行 MUST 只发生在统一的工具执行入口:先过沙箱/白名单检查位,再执行,结果含成功标识、内容、错误信息、是否可重试;失败不吞异常。
- **FR-006**: 每次工具调用不论成败 MUST 写入工具调用审计(含成功标识与错误原因两个字段);模型调用与工具调用 MUST 都携带会话标识以便关联。
- **FR-007**: 系统 MUST 提供统一的处理入口供 CLI/Web/定时三种触发源调用;处理期间工具可取到当前 Profile;处理结束(含异常)MUST 清除;结束后 MUST 持久化会话。
- **FR-008**: 系统 MUST 按 Profile 的启动文件与技能字段读取 `.oryxos/` 下文件拼接上下文;每次组装 MUST 重新读取、不缓存;Profile 显式引用的文件缺失 MUST 报错,启动文件缺失至少 WARN。
- **FR-009**: 系统 MUST 持久化工具调用审计表(实体、仓储、手工建表脚本,与模型调用审计同口径)。
- **FR-010**: 工具并行调用、Agent 间委托、流式输出、上下文压缩 MUST NOT 在本节实现。

### Key Entities

- **会话(Session)**: 一次对话的全部状态与消息序列,带会话标识、所属 Profile。本节仅需最小契约,完整实现属第 18 节。
- **工具调用(ToolCall)**: 模型提出的一次工具调用请求(工具名与入参)。
- **工具结果(ToolResult)**: 成功标识、内容、错误信息、是否可重试。
- **工具调用审计(ToolInvocation)**: 每次工具调用一条:会话标识、工具名、入参、成功标识、错误原因、时间。
- **当前 Agent 上下文(ProfileContext)**: 处理期间对工具可见的当前 Profile,线程内有效、结束必清。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 模型永远要求调工具时,处理在恰好“最大轮数”次模型调用后终止,100% 返回收尾提示。
- **SC-002**: 任何一次工具调用(成功或失败)在审计中都有且仅有一条对应记录,覆盖率 100%。
- **SC-003**: 历史超过 N 轮时,提示中的历史轮数不超过 N。
- **SC-004**: 处理结束(含异常)后,当前 Agent 身份残留次数为 0。
- **SC-005**: 修改启动/技能文件后,下一次对话 100% 读到新内容。
- **SC-006**: 五个验收测试类全部通过,且全量构建与代码检查全绿。
- **SC-007**: 用真实模型可完整跑通“查天气→给穿搭建议”多轮对话(人工验收)。

## Assumptions

- 依赖第 16 节已交付的 Profile、ProfileLoader、ProfileRegistry、模型调用服务(带会话标识)与模型调用审计。
- 第 18/20/22 节的会话管理、工具注册与结果、长期记忆尚未交付;本节仅建最小接口占位(已与用户确认),后续节补实现且不破坏签名。
- 沙箱具体校验留第 24 节,本节在工具执行入口预留检查位。
- 核心阶段上下文策略仅为“保留最近 N 轮”,不做压缩。
- 实现遵循 constitution:自实现循环、禁用框架自动工具执行、同步阻塞+虚拟线程。
